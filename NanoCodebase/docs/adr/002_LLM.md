# ADR 002: LLM Implementation

- **Status:** Implemented - Requires Evaluation
- **Deciders:** PhoenixWolf0 (Nathaniel Norman)
- **Date:** 2026-09-25

---

## 1. Context & Problem Statement

As part of the current system refactor, the LLM subsystem is being reimplemented. This provides an opportunity to 
reconsider the original implementation and improve its resource efficiency, maintainability, and overall architecture.

The LLM is expected to be one of the robot's most memory-intensive workloads. Because the robot operates with limited 
onboard resources, excessive RAM usage by the LLM may reduce the resources available to other subsystems or limit the 
size and quality of the models we can run.

We therefore need to determine how the LLM should be implemented and integrated so that memory usage is minimized 
without unnecessarily sacrificing functionality, performance, or maintainability.

---

## 2. Decision Drivers (Goals & Constraints)

TTFT - Time to first token

- **Goal 1:** Replies must maintain sufficient conversational quality, short-term contextual awareness, 
and personality for natural interaction with the robot.
- **Goal 2:** TTFT should remain <1s during normal operation when the model is already loaded.
- **Goal 3:** Cold-starting the LLM runtime from local storage should take <5s.
- **Goal 4:** The implementation should provide sufficient control over inference and memory-related parameters to
allow optimization for the robot's hardware.
- **Goal 5:** Integration complexity should remain reasonable and should not require maintaining a custom inference
engine.
- **Constraint:** The complete LLM runtime must be able to run at 4~5gb of RAM.

---

## 3. Options Considered

### Option 1: Ollama + Gemma 3 4B
Continue using the architecture from the previous implementation.

- **Pros:**
  - Already implemented and previously tested within the project. 
  - Requires relatively little setup and configuration. 
  - Provides a convenient API and model-management workflow. 
  - Reduces the amount of inference-specific code maintained by the project.
- **Cons:**
  - Provides less direct control over the underlying inference runtime. 
  - Adds another service/runtime layer between the robot software and the model. 
  - Makes fine-grained memory and inference optimization less straightforward. 
  - May consume resources for functionality that is not required.
  - Out of date LLM.
### Option 2: llama-cpp-python + Gemma 4 E4B
Run the larger Gemma 4 candidate directly through llama-cpp-python.

- **Pros:**
  - Provides direct access to llama.cpp runtime configuration, allowing lower-level inference and memory-management
parameters to be tuned for current hardware. 
  - Removes the need to run and communicate with a separate Ollama service. 
  - Gives direct control over model loading, unloading, and inference lifecycle. 
  - Expected to provide greater model capability than the smaller E2B variant.

### Option 3: llama-cpp-python + Gemma 4 E2B
Run the smaller Gemma 4 candidate directly through llama-cpp-python.

- **Pros:**
  - Provides the same low-level control as Option 2.
  - Lower model memory requirements leave more RAM available for other robot subsystems.
  - Smaller model weights should improve model-loading time. 
  - Lower compute requirements should improve the likelihood of meeting the TTFT target. 
- **Cons:**
  - Lower model capacity may reduce conversational quality, reasoning ability, instruction following, or
personality consistency relative to E4B.
  - May require more careful prompting or better context management to compensate for reduced model capability.

---

## 4. Decision & Justification

**Chosen Option:** Option 2 — llama-cpp-python + Gemma 4 E4B

### Rationale

Using llama-cpp-python gives the application more direct control over the underlying llama.cpp runtime than the previous
Ollama-based architecture. This allows greater control over model loading, and memory parameters to be tuned specifically
for the project constraints.

The E4B model was selected over the E2B variant because its greater model capacity is expected to provide better 
conversational quality, instruction following, reasoning, and personality consistency. Conversational interaction is a 
primary feature of the robot, so preserving LLM capability is considered important enough to initially accept the E4B 
model's higher memory and compute requirements.

However, this decision is conditional on the implementation satisfying the resource and performance requirements
defined in this ADR. In particular, the E4B implementation must operate within the available RAM budget without
unacceptably affecting other robot subsystems.

If evaluation shows that the E4B model cannot reliably satisfy the RAM, cold-start, or TTFT requirements after 
reasonable optimization, Option 3 (llama-cpp-python + Gemma 4 E2B) should be evaluated as the primary fallback.
